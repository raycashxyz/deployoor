# Developer flows

What day-to-day work looks like with deployoor, and what it replaces — measured against [Hardhat Ignition](https://hardhat.org/ignition), the official Hardhat deploy tool.

Not a feature checklist. Features get added, and Ignition has several features deployoor doesn't ([listed at the end](#what-ignition-and-hardhat-deploy-do-that-deployoor-does-not)). What doesn't change is the shape of the work, and that comes from one decision: **a deploy is compiled artifacts plus a viem wallet.** Pass the chain and the signer in, read the artifacts from whatever compiled them, and every flow below falls out of it.

Deployment should stop being a framework feature — the move data access already made, when an ORM stopped being something your web framework handed you and became a library you call from any runtime.

:::info
Checked against **July 2026** releases: Hardhat 3.11, Ignition 3.1.8, hardhat-deploy 2.0.10, rocketh 0.19.9. If something is out of date, [open an issue](https://github.com/raycashxyz/deployoor/issues).
:::

## Why hardhat-deploy isn't the main comparison

hardhat-deploy v2 covers similar ground, and covers it well. It's largely absent here for a structural reason rather than a dismissive one: it is a Hardhat plugin. Artifacts, network list, and accounts all arrive from the Hardhat runtime, and removing that dependency is the reason deployoor exists — so "which is better" collapses into a question you answer before picking either tool: do you want your deploy layer inside a framework?

[rocketh](https://rocketh.dev), the engine underneath it, is the fairer like-for-like, because it genuinely does run standalone with its own CLI and no Hardhat. There the difference isn't framework coupling but wallet ownership: `AccountDefinition` is `EIP1193Account | string | number`, so an account is _named to_ the tool rather than _passed to_ it, and a viem `Account` cannot reach a deploy call by any route. Everything below still applies, with "config" meaning `rocketh/config.ts`.

## Getting to your first deploy

**With deployoor** — a generate step, then a script. `deployoor generate` reads your artifacts and emits one typed function per contract, so mistakes are compile errors in your editor and in CI.

The block below is type-checked when these docs build — hover `CounterArgs`, and note that both errors are real `tsc` output rather than annotations:

```ts twoslash
// @errors: 2322 2339
import { defineDeployer } from "deployoor";
import type { PublicClient, WalletClient } from "viem";
const counterArtifact = {
  name: "Counter",
  abi: [
    { type: "constructor", inputs: [{ name: "initial", type: "uint256" }], stateMutability: "nonpayable" },
    { type: "function", name: "inc", inputs: [], outputs: [], stateMutability: "nonpayable" },
  ],
  bytecode: "0x60",
  metadata: {
    fullyQualifiedName: "src/Counter.sol:Counter",
    compilerVersion: "0.8.24",
    standardJsonInput: { language: "Solidity", sources: {}, settings: {} },
    libraryPlaceholders: {},
  },
} as const;
const getOrDeployCounter = defineDeployer(counterArtifact, {});
declare const walletClient: WalletClient;
declare const publicClient: PublicClient;
// ---cut---
// `args` comes from Counter's constructor, not from a generic array:
type CounterArgs = Parameters<typeof getOrDeployCounter>[0]["args"];
//   ^?

const { contract } = await getOrDeployCounter({ walletClient, publicClient, args: ["1"] });
await contract.write.inkrement();
```

No module to author, no network list, no accounts stanza. `deployoor.config.ts` is optional and holds output paths and plugins — never keys or chains.

**What it replaces.** Ignition needs three files and a CLI flag before the first contract goes out. Networks and signers are declared in config, and a chain you haven't listed is a chain you can't deploy to — there's no documented way to connect to an arbitrary RPC ad hoc:

```ts
// hardhat.config.ts
export default {
  plugins: [hardhatIgnitionViemPlugin],
  networks: {
    sepolia: {
      type: "http",
      chainType: "l1", // l1 | op | generic
      url: configVariable("SEPOLIA_RPC_URL"),
      accounts: [configVariable("SEPOLIA_PRIVATE_KEY")], // key material, named to the tool
    },
  },
};
```

Then the deployment, as a module:

```ts
// ignition/modules/Counter.ts
export default buildModule("CounterModule", (m) => {
  const counter = m.contract("Counter", [0n]);
  m.call(counter, "inc");
  return { counter };
});
```

From the shipped types, nothing there is checked against your ABI by TypeScript:

```ts
contract<ContractNameT extends string>(contractName: ContractNameT, args?: ArgumentType[], …)
call<ContractNameT extends string, FunctionNameT extends string>(contractFuture, functionName: FunctionNameT, args?: ArgumentType[], …)
type ArgumentType = BaseArgumentType | ArgumentType[] | { [field: string]: ArgumentType }
```

Ignition does validate futures against your compiled artifacts during deployment planning, so a misspelled contract or function name, or the wrong argument shape, is caught before any transaction is sent. The difference is _when_: those are deploy-run validation errors, not editor squiggles or a failing `tsc` in CI. Accounts are reached by index — `m.getAccount(accountIndex: number)` — and a module cannot branch on chain ID. The chain itself is chosen outside the code:

```bash
hardhat ignition deploy ./ignition/modules/Counter.ts --network sepolia
```

## Deploying to one chain

**With deployoor** — a Node program. You build the signer and the chain:

```ts
// scripts/deploy.ts — run with `tsx scripts/deploy.ts`
const account = privateKeyToAccount(process.env.PK as `0x${string}`);
const transport = http(process.env.RPC_URL);
const clients = {
  walletClient: createWalletClient({ account, chain: sepolia, transport }),
  publicClient: createPublicClient({ chain: sepolia, transport }),
};

const { contract } = await getOrDeployCounter({ ...clients, args: [0n] });
```

`account` is any viem `Account`: an encrypted keystore, AWS or GCP KMS, Turnkey, Privy, a Ledger, or a JSON-RPC account. deployoor hands the deployment transaction to the wallet client you supply — a local account signs in-process, a JSON-RPC account delegates to the provider — and never sees a secret either way. Swapping custody between test, staging, and production changes that one line and nothing else.

**What it replaces** — running the module, through the CLI above or the runtime:

```ts
const connection = await hre.network.create(); // needs the Hardhat runtime present
const { counter } = await connection.ignition.deploy(CounterModule);
```

## Deploying to many chains

**With deployoor** — a chain is an argument, so it's a loop:

```ts
for (const chain of [mainnet, base, optimism, arbitrum /* … */]) {
  const clients = clientsFor(chain, rpcUrls[chain.id]);
  await getOrDeployCounter({ ...clients, args: [0n] });
}
```

Each deploy records under its own `deployments/<chainId>-<network>/`. [`examples/multi-chain`](https://github.com/raycashxyz/deployoor/tree/main/examples/multi-chain) deploys across two chains and wires them as LayerZero peers in one script.

**What it replaces.** In **Hardhat 2** this isn't possible in one run: `hre.network` is a single connection fixed at startup by `--network`, so fifteen chains is fifteen CLI invocations sequenced in a shell script rather than in typed code. **Hardhat 3** makes it possible — `network.create()` holds several connections, each with its own Ignition helper — and still awkward: every chain must be declared in config, an Ignition deployment id is **permanently bound to one chain** (changing it errors with `HHE10900`), there's no official multi-chain example, and modules can't branch on chain ID, so per-chain differences live outside the module.

## Testing

**With deployoor** — the deployer you ship is the deployer under test. Swap the clients, keep the call:

```ts
import { createTestClients } from "@deployoor/testing";

const clients = await createTestClients(); // in-memory EVM + in-memory store
const { contract } = await getOrDeployCounter({ ...clients, args: [0n] });
expect(await contract.read.count()).toBe(0n);
```

Any runner, no Hardhat, no node, and nothing written to disk — `createTestClients` supplies an ephemeral store, so test deploys never touch your committed `deployments/`. Point the same call at `http(rpcUrl)` and it's a live-network test, including against a fork, which is just a transport aimed at `anvil --fork-url`. And because a chain is a client, multi-chain tests look like multi-chain deploys:

```ts
const a = await createTestClients();
const b = await createTestClients();
const ping = await getOrDeployPing({ ...a, args: [endpoint] });
const pong = await getOrDeployPong({ ...b, args: [endpoint] });
```

**What it replaces** — tests that run under Hardhat and take their chain from it:

```ts
import { network } from "hardhat"; // the test must run inside Hardhat
const { ignition } = await network.create();
const { counter } = await ignition.deploy(CounterModule);
```

The in-memory chain, the accounts, and the fixture helpers are all Hardhat's. Live-network testing is the same story from the other end — `--network sepolia`, resolved through the same config — so a test can't reach an undeclared chain, and can't run outside the framework at all.

## Running an ops script against contracts already live

**With deployoor** — the committed record is the source of truth, so an ops script is a script, using the same typed bindings your frontend has:

```ts
import { writeCounterInc } from "./src/generated"; // from `wagmi generate`
await writeCounterInc(config, { chainId: base.id });
```

**What it replaces.** In Ignition, post-deploy calls belong in a module as `m.call`, reconciled on the next run; for a one-off transaction you write a Hardhat script, create a connection, and fetch the contract through the connection's viem helper.

## Handing deployments to the frontend team

**With deployoor** — the record is already the interchange format, so you hand it to the tool the frontend team uses anyway:

```ts
// wagmi.config.ts
export default defineConfig({
  out: "src/generated.ts",
  plugins: [deployments({ path: "./deployments" }), actions()], // or react() for hooks
});
```

The same contract across chains folds into one entry with a `chainId → address` map. The generated file imports `viem`/`@wagmi/core` and never deployoor, so the frontend takes no dependency on your deploy tool. See [consumption](/guides/consumption).

**What it replaces.** Ignition ships nothing for this: addresses live in `deployed_addresses.json` keyed `Module#Future`, ABIs in `artifacts/<Module>#<Future>.json`, and you join them yourself — `wagmi`, `frontend`, and `typed` appear nowhere in its docs. For contrast, Foundry's `broadcast/…/<sig>-latest.json` is a transaction log with **no ABI** and a `contractName` that can be `null`; `@wagmi/cli`'s foundry plugin can scrape it (`includeBroadcasts`, off by default, only globs `run-latest.json`, skips factory deploys), and `vm.getDeployment` reads an address back in Solidity but can't feed an app.

## What Ignition and hardhat-deploy do that deployoor does not

- **Resumability** — Ignition's write-ahead journal and reconciliation let an interrupted deploy resume and adapt to module changes; `status` reports what executed, and `track-tx` repairs a transaction missing from the state when Ignition tells you to run it. deployoor writes records atomically and takes a lock, but a crash between broadcast and receipt needs manual recovery.
- **Bytecode-aware idempotency** — hardhat-deploy redeploys when compiled bytecode changed; deployoor reuses a record until you pass `force: true`, and only warns. [Roadmap.](https://github.com/raycashxyz/deployoor/blob/main/TODO.md)
- **Proxies, diamonds, CREATE2/CREATE3** — hardhat-deploy ships all of these; deployoor has none yet, so upgradeable contracts are better served there today.
- **Standalone re-verification** — `ignition verify <id>` and `rocketh-verify` are their own commands. deployoor's verifier plugins do fire on a reused deployment, so re-running the script retries a failed verification, but there's no `deployoor verify` yet.
- **Deploying through a Safe** — needs Safe's `CreateCall`, where the address arrives in an event rather than `receipt.contractAddress`. Ignition has no Safe path either; today you deploy via the Safe and `register` the address.
- **Reaching a deployment without its constructor args** — `getOrDeploy<Name>` requires `args` even when it only returns the recorded contract. Use the wagmi bindings for pure interaction.
- **Maturity** — Ignition is the official Hardhat tool on 3.x; deployoor is 0.x and pre-1.0 minors may break.

## Which to reach for

- **deployoor** — your team writes TypeScript, and you want the wallet and chain list to be code, one script serving as both test and production deploy, and a record any language can read. Runs over Hardhat v2/v3, Foundry, or plain `.sol` via tevm.
- **Hardhat Ignition** — you want the officially-supported path, prefer declaring a deployment over scripting it, and resumability of large multi-step deploys matters most.
- **hardhat-deploy v2 / rocketh** — you're happy inside Hardhat and want batteries included: proxies, diamonds, deterministic addresses, bytecode-diff redeploys.
- **`forge script`** — your team lives in Solidity. It pairs with deployoor, which reads `out/` directly: keep `forge build` and `forge test`, add typed TypeScript deploys, ops scripts, and integration tests over the same artifacts.

Adoption isn't all-or-nothing — `register` records a contract you didn't deploy, with no transaction, which is the basis of the [migration guide](/guides/migrate-from-hardhat-deploy).
