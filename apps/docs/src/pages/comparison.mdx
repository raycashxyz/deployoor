# Comparison

How deployoor relates to [hardhat-deploy](https://github.com/wighawag/hardhat-deploy) / [rocketh](https://rocketh.dev), [Hardhat Ignition](https://hardhat.org/ignition), and Foundry's `forge script` broadcasts.

Checked against each tool's current release, **July 2026**: hardhat-deploy 2.0.10, rocketh 0.19.9, Hardhat Ignition 3.1.8, Foundry 1.7.1. These tools are all actively maintained. If something here is out of date, [open an issue](https://github.com/raycashxyz/deployoor/issues).

:::info
Version details that decide whether a comparison applies:

- **hardhat-deploy v1 and v2 are different products.** v1 is ethers v5 on Hardhat 2; v2 is viem on Hardhat 3. Everything below refers to v2 unless it says otherwise.
- **rocketh is the engine underneath hardhat-deploy v2**, not its replacement. Same author, same monorepo, same release train.
  :::

## At a glance

|                                     | **deployoor**                                         | **hardhat-deploy v2 / rocketh**                         | **Hardhat Ignition**                          | **`forge script`**                        |
| ----------------------------------- | ----------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------- | ----------------------------------------- |
| Reads artifacts from                | Hardhat v2 **and** v3, Foundry, plain `.sol` via tevm | Hardhat 3                                               | Hardhat 3 (v2 via the `0.15.x` line)          | Foundry                                   |
| Deploy runs without a framework CLI | Yes — `tsx scripts/deploy.ts`                         | `rocketh` CLI (no Hardhat needed); browser too          | No — a Hardhat plugin                         | No — `forge script`                       |
| Address **and** ABI in one file     | Yes                                                   | Yes                                                     | No — split across two files                   | No — broadcasts carry no ABI              |
| chainId in the record path          | Yes — `deployments/<chainId>-<network>/`              | No — network name, chainId in a `.chain` sidecar        | Yes — `chain-<chainId>/`                      | Yes                                       |
| Signer                              | Any viem `WalletClient`                               | viem                                                    | viem **or** ethers (not both)                 | Solidity / keystore                       |
| Idempotency default                 | Record exists → reuse                                 | Bytecode changed → redeploy                             | Reconcile journal; changed future → **error** | None — `--resume` only retries failed txs |
| Typed app access outside the tool   | `@wagmi/cli` via `@deployoor/wagmi`                   | First-party `rocketh-export --ts`                       | None                                          | `@wagmi/cli` foundry plugin               |
| Proxies / diamonds                  | Planned                                               | Yes — UUPS, Transparent, ERC-173, ERC-1967, EIP-2535    | Via guides / `m.contractAt`                   | Manual                                    |

| Maturity                            | **0.x, early**                                        | 2.0.x, ~1.3k stars                                      | 3.1.x, official Hardhat tool                  | Stable                                    |

## Why deployoor exists

Three things we wanted, none of which is a missing feature in the tools above — they are preferences about shape, and together they are why deployoor is a separate project.

### The framework compiles; it does not own deploys or tests

Hardhat is good at compiling contracts. Deployment and testing are separate jobs, and a script that performs them should not depend on a framework runtime to exist. The same TypeScript test should run against a Hardhat node, anvil, a fork, an in-memory EVM, or Sepolia by swapping a transport — not by switching frameworks.

That extends to accounts, and it is the difference we care about most: **hardhat-deploy names accounts; deployoor takes signers.** In hardhat-deploy v2 an account is declared to the tool, as an index, an address, or a `protocol:` string:

```ts
// rocketh/config.ts — accounts declared to the deploy tool
accounts: {
  deployer: { default: 0 },   // index into the provider's eth_accounts
  admin: { default: 1 },
},
```

Its `AccountDefinition` is `EIP1193Account | string | number` — there is no object form, so you cannot hand a deploy call a viem `Account`. Custody instead becomes the tool's concern: a `signerProtocols` entry in config, returning an EIP-1193 shim. That extension point is real (ENS ships one) but the only implementation shipped is `privateKey`.

deployoor has no accounts config, on purpose. The signer is a parameter, so custody stays in your code and the tool never has an opinion about it:

```ts
// accounts.ts — yours, plain viem, nothing registered with a tool
import { privateKeyToAccount, toAccount } from "viem/accounts";

export const deployer = privateKeyToAccount(process.env.DEPLOYER_KEY as `0x${string}`);

// the sensitive one never holds a key in the process: a custom Account backed by
// hardware or a remote signer, with whatever confirmation you want around it
export const treasury = toAccount({ address: TREASURY, signMessage, signTransaction, signTypedData });
```

Named accounts come along for free, because a name is what `export const` is. The indices in an `accounts` map resolve against an HD wallet, so derive them the same way and give them names:

```ts
// accounts.ts — the named-accounts feature, as ordinary imports
import { mnemonicToAccount } from "viem/accounts";

const m = process.env.MNEMONIC as string;
export const deployer = mnemonicToAccount(m, { addressIndex: 0 });
export const admin = mnemonicToAccount(m, { addressIndex: 1 });

// per-network variation is a lookup, not a config schema
export const signerFor = (chainId: number) => (chainId === 11_155_111 ? admin : deployer);
```

Now `import { deployer } from "./accounts"` is the whole feature, and it type-checks. A per-environment `{ default: 0, sepolia: 1 }` map exists to solve referring to an account by name when accounts are declared to a tool — which stops being a problem once they are values in your own module.

Two more things follow that a config field cannot give you.

**Your custody options are not a plugin catalogue.** viem only asks an account for `address` plus `signMessage` / `signTransaction` / `signTypedData` — and a deploy calls only `signTransaction`. So anything that can produce a secp256k1 signature works: an encrypted keystore, AWS or GCP KMS, Turnkey, Coinbase CDP, Privy or Dfns server wallets, a Ledger behind `@ledgerhq/hw-app-eth`, or a JSON-RPC account where a node, Frame, or Clef signs and no key exists in the process at all. None of that needs anything from deployoor, or a release from us.

**Custody becomes testable, and stops drifting between environments.** An `accounts.ts` that picks a derivation path, refuses mainnet without confirmation, or routes the treasury to hardware is ordinary code you can unit-test. A per-network config stanza is not, and it is exactly the part your tests never execute. The deploy script itself is then byte-identical from a tevm test to CI to a mainnet Ledger run — the only thing that changes is which `Account` you construct.

**And deployoor has no opinion about secrets, because it never sees one.** Where your key or mnemonic comes from — a shell env var, Vault, 1Password, SOPS, AWS Secrets Manager, an operator typing it, or nowhere at all because a Ledger holds it — is settled before an `Account` exists. Hardhat 3 instead ships its own encrypted keystore, which is a real one (scrypt + AES-GCM-SIV) and also demonstrates why we would rather not: a plaintext env var of the same name silently takes precedence over the vault, and the keystore is skipped entirely under CI, so the automated path is back to env secrets regardless. Secrets management is somebody's whole product; a deploy tool is a poor place to re-solve it.

### Networks are values too

The same inversion applies one level out. A viem client takes a `chain` object and a transport, so the caller decides where a deploy goes:

```ts
const walletClient = createWalletClient({ account, chain: sepolia, transport: http(rpcUrl) });
```

Any RPC URL, any chain, decided at the call site — which is what lets one script deploy to several chains by constructing several clients, as [`examples/multi-chain`](https://github.com/raycashxyz/deployoor/tree/main/examples/multi-chain) does with Ping on Sepolia and Pong on Base Sepolia.

In Hardhat, networks are a registry the tool owns: they must be declared in `hardhat.config.ts` and referenced by name, and there is no documented way to connect to an arbitrary RPC URL ad hoc. Hardhat 3 does let you hold connections to several chains in one process via `network.create()`, so multi-chain scripts are possible — but the set of reachable chains is still config, a `--network` flag supplies a default connection alongside any you create programmatically, and connections carry a `chainType` (`l1` / `op` / `generic`) that shapes simulated-network behaviour and gates typed methods like `estimateL1Gas`. That is useful for high-fidelity local simulation of an OP stack; it is a concept a deploy script does not need.

viem already draws a clean line between wallets and everything else, and we would rather not put a config file in front of it.

### Deployers take a wallet client, not an artifact and an address

A generated deployoor deployer asks for viem clients and nothing else:

```ts
const { contract } = await getOrDeployCounter({ walletClient, publicClient, args: [7n] });
await contract.write.setNumber([42n]); // typed viem contract object, immediately
```

Which account and which chain are properties of the client you pass, so the same function deploys to anvil in a test, to Sepolia from CI, and to mainnet from a Ledger. Nothing about the deployer is bound to one chain or one signer.

hardhat-deploy takes the artifact plus an account and hands back a deployment record. Reads and writes then go through the environment, or through a viem wrapper you ask the environment for:

```ts
// deploy → a deployment record, not a contract
const deployment = await deploy("GreetingsRegistry", {
  account: deployer,
  artifact: artifacts.GreetingsRegistry,
  args: [""],
});

// write → environment-provided execute, account named in config
await env.execute(GreetingsRegistry, {
  account: env.namedAccounts.deployer,
  functionName: "setMessage",
  args: ["hello"],
});

// read → ask the environment to wrap the record as a viem contract
const contract = env.viem.getContract(deployment);
await contract.read.messages([deployer]);
```

We wanted the viem object on the first line, without `env` in the middle.

### Functional composition over an environment object

deployoor is plain functions over values. There is no `env` threaded through your script, and viem is a peer dependency you own rather than a capability the tool grants you. hardhat-deploy reaches viem through an extension registered in config:

```ts
// rocketh/config.ts — viem arrives as one of several spread-in extensions
import * as deployExtension from "@rocketh/deploy";
import * as readExecuteExtension from "@rocketh/read-execute";
import * as viemExtension from "@rocketh/viem";

const extensions = { ...deployExtension, ...readExecuteExtension, ...viemExtension };
```

deployoor imports viem directly, so a viem release is usable as soon as you bump your own dependency, with no intermediate package in the path.

## What this buys, concretely

**One tool across Hardhat, Foundry, and plain Solidity.** None of the others span Hardhat _and_ Foundry. rocketh's core is EIP-1193 + abitype and advertises framework-agnosticism, but ships no Foundry artifact loader, docs, or template — Hardhat is the only toolchain it documents. deployoor reads Hardhat v2 `.dbg.json` build-info, Hardhat v3's split `build-info/<id>.json`, Foundry `out/`, and compiles plain `.sol` with tevm.

**The record is one flat file.** `deployments/<chainId>-<network>/<Contract>.json` holds the address, full ABI, chainId, constructor args, tx hash, deployer, and compiler settings together. Ignition splits addresses from ABIs and joins them on a `Module#Future` string. Foundry broadcasts carry no ABI. hardhat-deploy uses the same one-file idea, keyed by Hardhat network name with chainId in a `.chain` sidecar, so the path alone does not identify the chain.

**Consumption is delegated.** deployoor stops at the record and hands it to [`@wagmi/cli`](https://wagmi.sh/cli), so typed access comes from the wagmi team's codegen and your app depends on `viem`/`@wagmi/core`, never on deployoor. hardhat-deploy ships its own exporter, `rocketh-export`, in its own format.

**The same deployers run in tests.** [`@deployoor/testing`](/guides/testing) boots an in-memory EVM ([tevm](https://tevm.sh)) as viem clients plus an in-memory store, so the exact `getOrDeploy` function you ship runs under vitest with no node and no disk writes.

## Where the others are ahead

- **Bytecode-aware idempotency.** hardhat-deploy compares compiled bytecode with the metadata trailer stripped and redeploys when the code actually changed. deployoor reuses a recorded deployment until you pass `force: true`, so editing a contract and re-running keeps the old address and emits a warning. [Bytecode-diff redeploy is on the roadmap](https://github.com/raycashxyz/deployoor/blob/main/TODO.md).
- **Proxies, diamonds, and deterministic addresses.** hardhat-deploy ships ERC-1967 / Transparent / UUPS / ERC-173 proxies, EIP-2535 diamonds, and CREATE2/CREATE3. deployoor has none of these yet, so upgradeable contracts are better served there today.
- **Resumability.** Ignition's write-ahead journal, batched execution, fee bumping, and `ignition status` / `transactions` / `track-tx` recover a half-finished deploy. deployoor writes records atomically and takes a coarse lock, but a crash between broadcast and receipt needs manual recovery.
- **Standalone re-verification.** `rocketh-verify` and `ignition verify <id>` read a saved deployment and submit it as their own command, with no deploy script involved. deployoor verifies through deploy-lifecycle plugins: they also fire on a reused deployment when the artifact metadata is still available, so re-running your deploy script retries a verification that failed — never pass `force: true` for this, as that bypasses the record and deploys a new contract at a new address. What is missing is the standalone entry point, [`deployoor verify` from committed records](https://github.com/raycashxyz/deployoor/blob/main/TODO.md).
- **Maturity.** Ignition is the official Hardhat tool on 3.x, bundled as a peer of both recommended toolboxes. deployoor is 0.x; pre-1.0 minor releases may break.
- **Named accounts** are listed here in most comparisons, including earlier versions of this one. They belong under [accounts as values](#the-framework-compiles-it-does-not-own-deploys-or-tests) instead: naming an account is what `export const` does, and per-network variation is a `chainId` lookup.

## When to use which

**Reach for deployoor when** you want one deploy tool across Hardhat and Foundry, a committed flat-JSON record any language can read, plain TypeScript deploy scripts with your own viem signer (a local key, a Ledger, Privy, Turnkey), and typed access through `@wagmi/cli` — plus the same deploy functions running in in-memory EVM tests.

**Reach for hardhat-deploy v2 / rocketh when** you're on Hardhat 3 and want the mature, batteries-included option: proxies and diamonds, deterministic addresses, named accounts, and bytecode-diff redeploys. Or when you want a deploy system with no Hardhat at all and Hardhat-shaped artifacts are fine.

**Reach for Hardhat Ignition when** you want the officially-supported Hardhat path, you like describing a deployment declaratively, and resumability of large multi-step deploys matters more than what the on-disk record looks like.

**Stay with `forge script` when** your team lives in Solidity and you're happy reading addresses out of broadcast JSON — or pair it with deployoor, which reads Foundry's `out/` directly.

### Two things about Foundry worth stating plainly

Because they're easy to omit and would make the row above look unfair:

- **There is a read-back cheatcode.** `vm.getDeployment(name[, chainId])` has shipped in forge-std since late 2024 and finds an address in `broadcast/` without `fs_permissions`. Its limits are real, though: it returns an address and nothing else (no ABI, no args, no compiler), it's callable only from Solidity — so it can't feed a frontend or CI — it's keyed on the same `contractName` that goes `null` when bytecode matching fails, and it's undocumented (every `/reference/cheatcodes/get-deployment*` page 404s).
- **`@wagmi/cli`'s foundry plugin can read broadcasts.** `includeBroadcasts` (added Jan 2026, **off by default**) scrapes deploys out of `broadcast/`. It only globs `run-latest.json`, so a script run with `--sig "deploy()"` is invisible to it; it only counts top-level `CREATE`/`CREATE2`, so factory deploys are skipped; and it's last-writer-wins across files with no timestamp ordering.

Foundry's own multi-chain guide recommends hand-writing a deployment manifest with `vm.serializeAddress` + `vm.writeJson` into `deployments/<chainId>.json`, and lists "track all deployments in version control" as a best practice. That hand-rolled manifest is, more or less, the artifact deployoor generates for you — with the ABI, args, and compiler settings attached.

## They compose

deployoor is not an all-or-nothing adoption. `register` records a contract you didn't deploy — an existing hardhat-deploy address, USDC, a factory-created contract — with no transaction:

```ts
await register({ publicClient, deploymentName: "Token", address: "0x…", abi: tokenAbi });
```

That's the basis of the [migration guide](/guides/migrate-from-hardhat-deploy): bring your existing addresses into `deployments/` and adopt deployoor for the next deploy, without redeploying anything.
