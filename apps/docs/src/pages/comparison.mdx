# Comparison

Same jobs, side by side: [hardhat-deploy](https://github.com/wighawag/hardhat-deploy) / [rocketh](https://rocketh.dev), [Hardhat Ignition](https://hardhat.org/ignition), and deployoor.

This page is not a feature checklist. Features get added, and the tools above have several deployoor doesn't — those are [listed at the end](#what-the-others-do-that-deployoor-does-not). What doesn't change is the shape of the work, which comes from one decision: **a deploy is compiled artifacts plus a viem wallet.** Pass the chain and the signer in, read the artifacts from whatever compiled them, and every flow below falls out of that.

Deployment should stop being a framework feature — the move data access already made, when an ORM stopped being something your web framework handed you and became a library you call from any runtime.

:::info
Checked against **July 2026** releases: hardhat-deploy 2.0.10, rocketh 0.19.9, Hardhat Ignition 3.1.8, Foundry 1.7.1. **hardhat-deploy v1 and v2 are different products** — v1 is ethers v5 on Hardhat 2, v2 is viem on Hardhat 3; this page means v2. **rocketh is the engine underneath v2**, not its replacement. If something is out of date, [open an issue](https://github.com/raycashxyz/deployoor/issues).
:::

## Deploy to one chain

**Ignition** — describe the deployment in a module, then run it through the CLI or the Hardhat runtime:

```ts
// ignition/modules/Counter.ts
export default buildModule("CounterModule", (m) => {
  const counter = m.contract("Counter", [0n]);
  m.call(counter, "inc");
  return { counter };
});
```

```ts
// scripts/deploy.ts
import hre from "hardhat";
const connection = await hre.network.create();
const { counter } = await connection.ignition.deploy(CounterModule);
```

`hardhat ignition deploy ./ignition/modules/Counter.ts --network sepolia`. The signer comes from `networks.sepolia.accounts` in config; the chain comes from `--network`.

**hardhat-deploy** — a script, with the account named in `rocketh/config.ts`:

```ts
const deployment = await deploy("Counter", {
  account: deployer, // a name, resolved from config
  artifact: artifacts.Counter,
  args: [0n],
});
await env.execute(Counter, { account: env.namedAccounts.deployer, functionName: "inc", args: [] });
```

**deployoor** — a Node program. You construct the signer and the chain, and get a typed contract back:

```ts
// scripts/deploy.ts — run it with `tsx scripts/deploy.ts`
const account = privateKeyToAccount(process.env.PK as `0x${string}`);
const transport = http(process.env.RPC_URL);
const clients = {
  walletClient: createWalletClient({ account, chain: sepolia, transport }),
  publicClient: createPublicClient({ chain: sepolia, transport }),
};

const { contract, freshDeploy } = await getOrDeployCounter({ ...clients, args: [0n] });
if (freshDeploy) await contract.write.inc();
```

No module to author, no runtime to boot, and nothing named in a config file. `account` is any viem `Account` — a keystore, KMS, Turnkey, Privy, a Ledger, or a JSON-RPC account where no key exists in the process. deployoor never sees a secret.

## Deploy to fifteen chains

**Hardhat** — each chain must be declared in `hardhat.config.ts`; there is no documented way to connect to an arbitrary RPC ad hoc. Hardhat 3 can hold several connections in one process, so this is possible, but there's no official multi-chain example and an Ignition deployment id is permanently bound to one chain. In practice teams loop the CLI over `--network` in a shell script.

**deployoor** — a chain is an argument, so it's a loop over clients in one file:

```ts
for (const chain of [mainnet, base, optimism, arbitrum /* … */]) {
  const clients = clientsFor(chain, rpcUrls[chain.id]);
  await getOrDeployCounter({ ...clients, args: [0n] });
}
```

Each deploy records under its own `deployments/<chainId>-<network>/`. [`examples/multi-chain`](https://github.com/raycashxyz/deployoor/tree/main/examples/multi-chain) does this across two chains and wires them as LayerZero peers in the same script.

## Test

**Ignition** — tests run inside Hardhat, deploying the module through a connection:

```ts
import { network } from "hardhat";
const { ignition } = await network.create();
const { counter } = await ignition.deploy(CounterModule);
assert.equal(await counter.read.count(), 0);
```

**deployoor** — the deployer you ship is the deployer under test. Swap the clients, keep the call:

```ts
import { createTestClients } from "@deployoor/testing";

const clients = await createTestClients(); // in-memory EVM + in-memory store
const { contract } = await getOrDeployCounter({ ...clients, args: [0n] });
expect(await contract.read.count()).toBe(0n);
```

Any runner, no Hardhat, no node, no disk. And because a chain is a client, multi-chain tests work the same way as multi-chain deploys — two independent chains in one test file:

```ts
const a = await createTestClients();
const b = await createTestClients();
const ping = await getOrDeployPing({ ...a, args: [endpoint] });
const pong = await getOrDeployPong({ ...b, args: [endpoint] });
```

## Run an ops script against contracts already deployed

**hardhat-deploy** — through the environment, with the account named in config:

```ts
await env.execute(Counter, { account: env.namedAccounts.deployer, functionName: "inc", args: [] });
```

**Ignition** — post-deploy calls belong in a module as `m.call`, which is reconciled on re-run; for an ad-hoc transaction you write a Hardhat script and fetch the contract through the connection's viem helper.

**deployoor** — the committed record is the source of truth, so an ops script is a script. The generated wagmi bindings give you the same typed access your frontend uses, addresses included:

```ts
import { writeCounterInc } from "./src/generated"; // from `wagmi generate`
await writeCounterInc(config, { chainId: base.id });
```

Or re-call the deployer: it's idempotent, so it returns the recorded contract without sending a transaction.

## Hand deployments to the frontend team

**Ignition** — nothing ships for this. `deployed_addresses.json` holds addresses keyed `Module#Future`, ABIs live in `artifacts/<Module>#<Future>.json`, and you join them yourself. `wagmi`, `frontend`, and `typed` appear nowhere in the Ignition docs.

**hardhat-deploy** — first-party and good: `rocketh-export -e <env> --ts src/contracts.ts` emits `export default { … } as const` with `{ chain, name, contracts: { Name: { abi, address, startBlock } } }`. Its own format.

**Foundry** — `broadcast/<Script>.s.sol/<chainId>/<sig>-latest.json` is a transaction log with **no ABI**, and `contractName` can be `null`. `@wagmi/cli`'s foundry plugin can scrape it via `includeBroadcasts` (off by default, only globs `run-latest.json`, skips factory deploys). Solidity can read an address back with `vm.getDeployment`, but it returns only an address and can't feed an app.

**deployoor** — the record is already the interchange format, so you delegate to the tool the frontend team already uses:

```ts
// wagmi.config.ts
export default defineConfig({
  out: "src/generated.ts",
  plugins: [deployments({ path: "./deployments" }), actions()], // or react() for hooks
});
```

The same contract across chains folds into one entry with a `chainId → address` map. The generated file imports `viem`/`@wagmi/core` and never deployoor, so the frontend takes no dependency on your deploy tool. See [consumption](/guides/consumption).

## What the others do that deployoor does not

- **Bytecode-aware idempotency** — hardhat-deploy redeploys when compiled bytecode changed; deployoor reuses a record until you pass `force: true`, and only warns. [Roadmap.](https://github.com/raycashxyz/deployoor/blob/main/TODO.md)
- **Proxies, diamonds, CREATE2/CREATE3** — hardhat-deploy ships all of these; deployoor has none yet, so upgradeable contracts are better served there today.
- **Resumability** — Ignition's journal, batching, fee bumping, and `status` / `track-tx` recover a half-finished deploy; deployoor needs manual recovery after a crash between broadcast and receipt.
- **Standalone re-verification** — `rocketh-verify` and `ignition verify <id>` are their own commands. deployoor's verifier plugins do fire on a reused deployment, so re-running the script retries a failed verification, but there's no `deployoor verify` yet.
- **Deploying through a Safe** — needs Safe's `CreateCall`, where the address arrives in an event rather than `receipt.contractAddress`. Ignition has no Safe path either; today you deploy via the Safe and `register` the address.
- **Reaching a deployment without its constructor args** — `getOrDeploy<Name>` requires `args` even when it only returns the recorded contract. Use the wagmi bindings for pure interaction.
- **Maturity** — Ignition is the official Hardhat tool on 3.x; deployoor is 0.x and pre-1.0 minors may break.

## Which to reach for

- **deployoor** — your team writes TypeScript, and you want the wallet and chain list to be code, one script serving as both test and production deploy, and a record any language can read. Runs over Hardhat v2/v3, Foundry, or plain `.sol` via tevm.
- **hardhat-deploy v2 / rocketh** — you're on Hardhat 3 and want batteries included: proxies, diamonds, deterministic addresses, bytecode-diff redeploys.
- **Hardhat Ignition** — you want the officially-supported path, prefer declaring a deployment over scripting it, and resumability matters most.
- **`forge script`** — your team lives in Solidity. It pairs with deployoor, which reads `out/` directly: keep `forge build` and `forge test`, add typed TypeScript deploys, ops scripts, and integration tests over the same artifacts.

Adoption isn't all-or-nothing — `register` records a contract you didn't deploy, with no transaction, which is the basis of the [migration guide](/guides/migrate-from-hardhat-deploy).
